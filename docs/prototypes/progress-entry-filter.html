过滤选项从哪来

选项命中条件数字来源
全部State 任意EntryItems.Count
异常Failed + SkippedStatsFailedCount + StatsSkippedCount
出错State == FailedStatsFailedCount
跳过State == SkippedStatsSkippedCount
已完成State == Completed需新增（现无此计数）

「异常」把出错和跳过合成一档 —— 用户点它的动机通常是「哪些没成功」，而不是严格区分。 「出错 / 跳过」单独一档则给需要区分的人。

三种形态的取舍

形态优点缺点
① 胶囊数字就在按钮上，一眼看到「有 4 条异常」；单击直达5 个胶囊在 500 窄窗口会换行，吃掉 1-2 行高度
② 下拉最省宽度，永远 1 行要点开才知道有几条异常 —— 恰恰是用户最想知道的
③ 分段比胶囊紧凑，数字挪到右侧显示右侧数字和分段控件分离，扫视时对不上

我倾向 ①胶囊，但只留 3 个：全部 / 异常 / 已完成 —— 「出错 / 跳过」收进「异常」里。 这样 500 宽窗口也排得下（约 300px）。多用几轮后如果确实需要区分，再加回。

两个必须一起做的小东西

空状态：过滤后 0 条时要显式提示 + 一个「显示全部」按钮，否则列表一片空白会被当成 bug（本原型已画，切到只有「出错」且没有失败项的状态可见）。

实时增减：过滤「已完成」时，一个 Pending 行跑完成必须立刻出现在列表里，Pending 时又必须立刻消失 —— 所以过滤判定挂在 State 变化上，不能只在切换过滤器时算一次。

实现要点（给后续计划用）

点做法
数据源 不动 _entryItems（全量、供 ActivateEntryByName 按 Name 匹配用）， 另开 ObservableCollection<EntryProgressItem> EntryViewItems 作为视图绑定源。 不要用 ICollectionView —— Avalonia 12 主包没有这个类型（实测 Avalonia.Controls.dll 零命中，也没引 CommunityToolkit 的集合视图）。
过滤时机 ①切换过滤器时全量重算一次；②UpdateEntryStatus 与 ActivateEntryByName 里 State 变化后单行增删（O(1) 判断 + O(n) 定位，5000 条可接受）。 只认 State —— Percent 每帧都变，不能触发重算。
顺序 过滤后保持播种原序（按 _entryItems 下标重排），不要按状态分组 —— 用户找的是「那个出错的文件在哪个位置」，分组会让他失去上下文。
滚动位置 切过滤器后滚回顶部。列表 MaxHeight=150 只有 6 行，保留滚动位置没有意义。
徽标数字 StatsFailedCount / StatsSkippedCount / StatsOverwrittenCount 已存在（ProgressViewModel.cs:851-857）， 直接绑。「已完成」缺一个计数 —— 需在 AccumulateTerminalBytes 旁边加 _entryCompletedCount，或从 _entryItems 现算（5000 条 <1ms，但每次都要算）。
空状态 过滤结果 0 条 → 显示「没有匹配的条目 + 显示全部」覆盖层。这一块 ProgressWindow.axaml 现在没有，必须新增。
持久化 我倾向实例级（关窗即忘），与「保持打开」「冲突策略下拉」一致。 若写进 AppSettings，会多一个 settingswiring 守卫要接的消费者。
5000 条上限 这是过滤器的软肋：MaxSeedEntryCount = 5000 是「超过就一条行都不建」（CompressFlow.cs:377 / ExtractFlow.cs:426）。 超过 5000 的包，列表本来就是空的，过滤器也就无从谈起。要不要放宽成「只播种异常项 + 最后 500 条」需要单独决策。

已经确认不做的

① 文件名搜索框 —— 5000 条实时过滤可接受，但本轮没验证过输入法与中文匹配，先不加。
② 按大小 / 时间排序 —— 播种顺序是压缩包内顺序，打乱后用户无法定位。
③ 把过滤器放到「详细」面板 —— 详细面板是并行通道（4-8 行），本来就没有几千条，不需要。
④ 多选交叉过滤（「出错 + 跳过」同时勾）—— 单选用胶囊已够，多选会引入「选中 0 项 = 显示全部还是显示空」的歧义。
