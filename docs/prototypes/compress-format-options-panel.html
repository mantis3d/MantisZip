压缩格式选项面板 — 界面改动原型

Phase 1 实施版（2026-10-19 更新）：改动 A（删「并行压缩组数」）已落地；改动 B（多线程依赖自适应）已暂缓——双机实测 MT 收益与 CPU 相关，一刀切会片面 → 原型中「取消自适应 → 多线程置灰」的联动演示仅作历史参考，Phase 1 三开关互相独立。
常驻科普提示（Phase 1 新增）：ZIP 面板「多线程压缩」下方灰字「收益与 CPU 配置相关：多核高配置提升明显；核心数较少时收益有限，甚至可能变慢。」—— 因提示独立成立、弱 CPU 用户在 Phase 1 即有风险窗口，故提前到本阶段（原计划归 Phase 2 Task 12 与基准测试捆绑）。
Phase 2 待实现：魔数检测 / 自适应规则 / 自定义格式魔数 hex / 本机基准测试。计划见 .omo/plans/进行中/adaptive-compress-ui-convergence.md。

对应「压缩设置」对话框 →「高级」标签页里的格式选项面板（DynamicFormatOptionsPanel）。
本原型演示两处改动：改动 A 删除「并行压缩组数」控件；改动 B 自适应关闭时多线程自动关闭并禁用。
受影响的界面共两处，都在这一页：① 压缩设置 → 高级 → 格式选项面板（改动 A + 改动 B）、② 设置 → 加速（改动 B）。

改动 A删除控件

改动前：ZIP 面板在多线程压缩下方还有一个 「并行压缩组数」 数字输入框（1–16，默认取 CPU 核数）， 只在勾选「多线程压缩」时显示。

改动后：该控件整块删除。组数改由引擎内部按 clamp(CPU 核数, 2, 8) 自动决定（本机 16 核 → 8 组）。

为什么删：实测该旋钮对速度没有正收益，反而在把组数设到核数以下时会静默限流—— 在 16 核机器上把组数设成 2，压缩只用到约 2 个核，耗时是设成 16 组的 约 3 倍（5.47s → 1.64s）。 组数本质上同时充当了「工作线程数」和「进度窗口通道行数」两个角色，耦合在一起就会误导用户。

改动 B联动禁用

取消勾选「自适应压缩」时，「多线程压缩」自动取消勾选并置灰禁用，并在下方出现一行灰色说明； 重新勾选「自适应压缩」后恢复可用，并还原用户之前的勾选状态。

为什么：多线程路径改用 7z 的 Deflate 压缩器（压缩率更高但更慢）。没有自适应先剔除已压缩文件时， 可压缩数据上「仅多线程」实测比完全不开多线程还慢约 1.5–1.8 倍。

连带效果（设置 → 加速 页）：改动 B 让「多线程压缩」依赖「自适应压缩」之后，下方三个区域的显隐关系也随之简化—— 「仅存储格式」等价于「多线程开启时」显示；「格式目录」「自适应规则」在「自适应开启且多线程关闭」时显示； 自适应关闭时三者全部隐藏（与既有规则一致）。

改动 C补联动

压缩对话框面板里，「自适应压缩」关闭时「魔数检测」置灰禁用（当前实现漏了这条联动）。

为什么：Core 里 ArchiveOptions.AdaptiveSmartDetect 的注释已写明「自适应开启时，对大文件做魔数增强识别。自适应关闭时无效」， 但 UI 没做这条联动，用户可以在自适应关闭时勾选一个根本不生效的选项。

备注（评审时需一并决定）：全仓检索确认该开关目前没有任何引擎消费者 —— 只有 UI 绑定、设置持久化和参数透传 （ArchiveOptions.AdaptiveSmartDetect → AdaptiveRuleMatcher.ResolveLevel(adaptiveSmartDetect:) 形参只写日志、不参与分支）。 也就是说这个选项当前是空转的，补联动只是修 UI 一致性，不改变压缩结果。

保留的既有行为不变

  • 设置 → 加速页里「魔数检测」随「自适应压缩」整行隐藏（自适应关闭时；规则 6：隐藏而非禁用）。
  • 两处形态不同（对话框＝置灰禁用 / 设置页＝整行隐藏），沿用各自现状；若要统一请告知。
  • 待压缩总量达到 ZIP32 上限（约 4GB）时，「多线程压缩」仍自动取消勾选 + 禁用并显示提示。
当前状态读数： 自适应 = 开 · 多线程 = 开 · 多线程可交互 = 是 · 引擎内部组数 = 8（自动） · 显示的组数控件 = 隐藏
