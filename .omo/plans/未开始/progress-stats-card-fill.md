## TL;DR

把统计卡行的那块 `Border` 背景改成**底纹进度条**：进度直接铺在卡片后面，不再占用独立一行。多态配色 —— 进行中按 `PercentComplete` 截断、**不确定态（准备 / 扫描）填充淡黄**、完成转绿 / 失败转红 / 取消转灰（判定统一走 `ProgressStatusKind`）。

**关键结论（2026-11-28 第四轮）：底纹不再只是「完整」档的装饰，而是这个窗口唯一的进度载体。** 五档全部有卡片行、全部有底纹，独立总进度条**彻底删除** —— 否则「完整档有底纹、其他档只有一根条」会让四档在视觉上像两个不同产品。

**同一批做五件事**：

1. **视图切换两行 → 一行五档**（极简 / 标准 / 详细 / 完整 / 列表），修掉「简约 vs 精简」词冲突与 `IsMinimalDensity` 无内容绑定的缺陷；「完整 \| 列表」之间插 1px 分隔线（列表不在「信息量递增」这条轴上）
2. **卡片行压进一行**（`MinWidth` 80 → 72、间距 24 → `ItemSpacing` 4 ⇒ 912px → 680px），窄窗（500）改为按可用宽度平分而不是折行
3. **轻量三档也放卡片**（§2.11）：极简 3 张（进度 / 已用 / 剩余）、标准 8 张（+ 已处理 / 总数量 / 总大小 / 速度 / 并行）、详细 9 张（并行换跳过 / 出错）。百分比、已用、剩余从底部行**搬进卡片**，轻量档的底部合并行整条消失
4. **列表档的卡行换成「可点过滤卡 + 只读信息卡」混排一行**（§2.9）：已完成 / 跳过 / 出错 / 已覆盖 / 全部 ⎮ 扫描 / 已压缩 / 仅存储。点卡即过滤列表、再点回「全部」。同时补齐「已完成」的计数（`ProgressViewModel` 现在只有跳过 / 出错 / 已覆盖三个累加器）
5. **完整档卡片补足第三行分母**（§2.12）：13 张卡统一「标题 / 数量 / 大小」三行，分母口径统一（分子 = 文件数，分母 = 大小）

配套：卡片行从横向 `StackPanel` 改 `WrapPanel`（Avalonia 的 `WrapPanel` **有** `ItemSpacing` / `LineSpacing`，不用手工算 `Margin`），独立总进度条删除。

HTML 原型（**以 `progress-window-full.html` 为准**，它把上面五件事全画全了，控制条 10 组开关可切）：`docs/prototypes/progress-window-full.html`
早期单点原型：`docs/prototypes/progress-stats-card-fill.html`（底纹与紧凑化）、`docs/prototypes/progress-filter-cards.html`（列表档可点卡）、`docs/prototypes/progress-filter-merge.html` / `progress-entry-filter.html`（已被取代的胶囊版）。

| Row 3 统计卡行 | 9 张三行统计卡（`StatsCardsPanel`） | `:701-705` 容器 / `:711` 卡片行 |

### 2.1 底纹落在哪

`StatsCardsPanel` 是 `Border`（`:701-705`），已有 `Background` / `CornerRadius` / `Padding`。把 `Background` 从静态 `{DynamicResource ThemeSurfaceBgBrush}` 改成 `MultiBinding`，输出一个 `LinearGradientBrush`：

> **2026-11-28 定案：挂卡片行，不挂整块信息区。** 用户原话：「我还是觉得只铺卡片行好些」。原型里两种都做过对比（控制条「③ 底纹挂」= 整块信息区 / 只挂卡片行）：挂整块时，无卡片行的三档会把底部合并行一起染色；既然第四轮让五档都有卡片行（§2.11），底纹跟着卡片行走才有统一底盘，切档时宽度也不跳。整块信息区那层不需要了，实现只改 `StatsCardsPanel` 一处。

```
GradientStops:
  [0]          填充色
  [offset]     填充色        ← offset = PercentComplete / 100
  [offset]     Transparent
  [1]          Transparent
```

写法直接照抄 `src/MantisZip.UI.Avalonia/Converters/BatchStatusConverters.cs:67-102` 的 `ProgressStatusToBackgroundConverter`（批处理行已经在用同一套 4-stop 渐变做行底纹，alpha = `0x59` ≈ 35%）。差别只有两点：它按 `BatchItemStatus` 选色，我们要按「不确定 / 确定 / 完成 / 失败」选色。

**为什么不用做法 B（卡片行下面叠一条细条）**：那是第三根进度条，不解决冗余。

### 2.2 多态配色

**判定依据用 `StatusKind` 而不是布尔标志**。`ProgressViewModel.cs:450-451` 有 `[ObservableProperty] private ProgressStatusKind _statusKind`，枚举定义在同文件 `:19-33`：

```csharp
public enum ProgressStatusKind { Preparing, Running, Paused, Completed, Failed, Cancelled }
```

它带变更通知（`partial void OnStatusKindChanged` 在 `:474`），可以直接绑。**不要绑 `HasFailures`**（`:900` 是只读计算属性，没有对应的 `OnPropertyChanged`，值变了 UI 不会刷新）。

| 状态 | 判定 | 填充色（浅色 / 深色） | alpha | 宽度 |
|---|---|---|---|---|
| 不确定（准备 / 扫描） | `IsIndeterminate == true` | `#FFB300` / `#FFC107` | **30% / 26%** | 满宽 |
| 进行中 | `StatusKind == Running` | `#2196F3` / `#64B5F6` | **35% / 35%** | `PercentComplete / 100` |
| 已暂停 | `StatusKind == Paused` | 同进行中 | 35%，整层 `Opacity=0.55` | `PercentComplete / 100` |
| 完成 | `StatusKind == Completed` | `#4CAF50` / `#66BB6A` | **20% / 22%** | 满宽 |
| 失败 | `StatusKind == Failed` | `#F44336` / `#EF5350` | **20% / 24%** | 满宽 |
| 已取消 | `StatusKind == Cancelled` | `#9E9E9E` / `#A0A0A0` | **20% / 22%** | 满宽 |

> **2026-11-28 改档说明**：原稿统一写「15% 透明」，原型里白底上几乎看不见。经用户确认「现在这个挺好」后按上表定稿 —— 进行中 35%（原 0x59≈35% 不变）、不确定 30% / 深色 26%、完成 / 失败 / 取消 20% 档（深色略高 2-4% 补偿深底）。暂停不换色，只降整层透明度到 0.55（原稿 50%）。
>
> 深浅两套主题都实测过：浅色进行中底纹叠在 `ThemeSurfaceBgBrush` 上是 `#9EC6E7`、深色是 `#3B576E`，两组对比度都够读。

- `IsIndeterminate` 优先于 `StatusKind`：扫描阶段（`:1157-1158`）会同时置 `StatusKind = Running` 和 `IsIndeterminate = true`，此时要显示黄色而不是蓝色。
- 暂停态用「同色 + 整层 `Opacity=0.55`」而不是换色，避免和「完成绿 / 失败红」抢注意力（原型确认：换黄会和扫描态撞）。

- 色值来源（已有）：`ThemeStatusWarning` 浅色 `#FFFFE082` / 深色 `#FF5C4A1E`；`ThemeStatusSuccess` 浅 `#FF4CAF50` / 深 `#FF2E7D32`；`ThemeStatusError` 浅 `#FFF44336` / 深 `#FFC62828`；`ThemeProgressFillBrush` 浅 `#FF2196F3` / 深 `#FF64B5F6`。
- **不用纯黄 `#FFFFEB3B`**：底纹上太刺眼，且主题里已有语义化 warning 色，自造会漂。
- **与「真警告」分层**：`ThemeStatusWarningBrush`（不透明）现在用于「磁盘空间不足」「同名文件冲突」这类真警告；底纹只取 20-30% 透明底，视觉上不抢。

### 2.3 不确定态为什么改成颜色而不是沿用滚动动画

`ProgressViewModel.cs` 有两处置 `IsIndeterminate = true`：

- `:1025` —— 准备态（开窗那一下）
- `:1158` —— 扫描阶段（`ArchivePhase.Scanning`，注释原文「总数未知：进度条滚动而非僵在 0%」），`:1162` 离开扫描阶段时置回 false

底纹是渐变，没有「滚动」可言。改用**满宽淡黄**表达「还没开始算进度」：

- 扫描阶段有动态计数文本兜底 —— `:1285` 会填 `ScanCountText = T("Progress_FileCount_Scanning", p.TotalFiles)`，卡片区「扫描」卡（`:720` 绑 `HasScanCount`）会实时变化，用户在文字上能看到「在动」。
- 准备态很短（就是开窗那一下），静止可接受。

**不做滚动动画**（省 1-2h）。如果实测觉得扫描期「一直黄着不动」像卡死，再单独加一个 `Animation` 循环扫光，不阻塞本计划。

### 2.4 卡片行改 WrapPanel 且压进一行

`ProgressWindow.axaml:711-713`：

```xml
<StackPanel Orientation="Horizontal"
            Spacing="{DynamicResource SpacingLg}"
            HorizontalAlignment="Center">
```

改成：

```xml
<WrapPanel Orientation="Horizontal"
           HorizontalAlignment="Center"
           ItemSpacing="{DynamicResource SpacingXxs}"
           LineSpacing="{DynamicResource SpacingXs}">
```

> **⚠️ 2026-11-28 纠正一个写错的前提**：本节早先写「`WrapPanel` 没有 `Spacing` 属性（Avalonia 与 WPF 都没有），间距要落到子项 `Margin` 上」—— **这是错的**。Avalonia 12 的 `WrapPanel` 比 WPF 多四个属性，已用项目实际依赖（`C:\Users\Admin\.nuget\packages\avalonia\12.1.2\lib\net10.0\Avalonia.Controls.xml`）确认：
>
> | 属性 | 类型 | 作用 |
> |---|---|---|
> | `ItemSpacing` | `double` | 主轴相邻项间距（**WPF 没有**） |
> | `LineSpacing` | `double` | 换行后的行距（**WPF 没有**） |
> | `ItemWidth` / `ItemHeight` | `double` | 强制统一项尺寸 |
> | `ItemsAlignment` | `WrapPanelItemsAlignment` | `Start` / `Center` / `End` |
>
> `ItemSpacing` 是标准 `double` 依赖属性，可以直接 `{DynamicResource SpacingXxs}`，**不需要** `Window.Styles` + `Margin` 那两套绕路方案（原「方案 i / ii」作废）。

**把卡片挤进一行**（「状态面板一行排下」的核心）。现状 9 × 80 + 8 × 24 = 912px 放不进 800 窗口，两个方向同时收：

| 项 | 现状 | 改后 | 节省 |
|---|---|---|---|
| 卡片 `MinWidth` | 80（模板内 10 处硬编码） | **72** | 9 × 8 = 72px |
| 卡片间距 | `SpacingLg` = 24（Normal 档） | **`SpacingXxs` = 4**（Compact 2 / Loose 6，跟紧凑度走） | 8 × 20 = 160px |
| **合计宽** | **912px** | **680px** | **−232px** |

**可用宽度账**（决定了间距能取多大）：窗口 800 → `RootGrid` 的 `SpacingMdThk` 左右各 16（`SpacingMd` = 16）→ 768 → 信息区 `Border` 边框 1×2 + `SpacingSmThk` 12×2 → 742 → `StatsCardsPanel` 的 `SpacingSmThk` 12×2 → **718px**。

| 紧凑度 | `ItemSpacing` | 9 张卡总宽 | 800 窗口 |
|---|---|---|---|
| Compact | 2 | 648 + 16 = 664 | ✓ |
| Normal | **4** | 648 + 32 = **680** | ✓ 余 38px |
| Loose | 6 | 648 + 48 = 696 | ✓ 余 22px |

⇒ 用 `SpacingXxs` 时**三档紧凑度都不会换行**。若改用 `SpacingXs`（4/8/12），Loose 档是 648 + 96 = 744 > 718 ⇒ 会换行，所以间距不能用 `SpacingXs`。

卡片内部同步收一档字号，否则 72px 装不下「已压缩 / 12 字」这类标签：

- 图标 16 → **14**
- 标签 `.r1 .lab` 11 → **10.5**
- 数值 `.r2` 15 → **13**（加 `line-height:1.3`）
- 副值 `.r3` 13 → **11.5**（加 `line-height:1.3`）

**500 宽窗口：平分而不是折行**（原型实测，用户问「卡片宽度变窄行不行？」）：可用宽只有 468px，8 张 72px 卡片必然折行。改法是把卡片改成弹性：

```xml
<!-- 窄窗时卡片按可用宽度平分（每张约 54px），而不是保持 72px 定宽后折行 -->
<Style Selector="WrapPanel > Border.card">
  <Setter Property="MinWidth" Value="72" />
</Style>
```

实现上给卡片模板的最外层 `Border` 设 `MinWidth="72"` 但**不设固定 `Width`**，`WrapPanel` 本身不参与弹性分配 ⇒ 需要切到 `UniformGrid` 或给卡片外层套一层 `Grid` 均分。**两种写法二选一，实施时按实测选**：

- **写法 A（推荐）**：卡片行容器在窄窗（`Bounds.Width < 600`）时切成 `UniformGrid Columns="8"`（每格自适应，卡片 `MinWidth=0`），宽窗切回 `WrapPanel`。缺点是切控件要写代码。
- **写法 B**：始终用 `WrapPanel`，卡片靠 `ItemWidth` 在窄窗设成 `(可用宽 - 7 × ItemSpacing) / 8`。缺点是 `ItemWidth` 要在 `SizeChanged` 里算。

**为什么压到 54px 也不截断文字**：卡片是三行竖排结构（标题 / 数量 / 大小各占一行），宽度只影响每行能放几个字。最长值是「41.76 MB」= 8 个字符，54px 在 9.5px 字号下放得下（原型实测 500 宽八张卡仍是一行、数值完整）。窄窗再补两条：

```
html[data-width="500"] .cards .card { padding: 1px 2px; }   /* 左右内边距从 4 收到 2 */
html[data-width="500"] .card .cv   { font-size: 12px; }     /* 数值 13 → 12 */
html[data-width="500"] .card .cl,
html[data-width="500"] .card .cs   { font-size: 9.5px; }    /* 标签与副值降一档 */
```

> **72px 的可行边界仍要真机验**：原型用 HTML 量的是近似值，Avalonia 的字号与 `MinWidth` 实际表现需在 500 / 800 / 1200 三档窗口宽度下各看一次。若 72px 下「已压缩」这类三字标签被挤到换行，退一步到 76px（9 × 76 + 8 × 4 = 716px，800 窗口刚好放下 718px 可用宽 —— 只剩 2px，很悬；更稳的是把标签缩成两字）。

### 2.5 独立总进度条：彻底删除

> **2026-11-28 变更**：本节早先的方案是「完整档隐藏、其他三档保留」（`IsVisible` 取反）。**第四轮之后这个方案作废** —— 既然五档都有卡片行、都有底纹（§2.11），独立总条在任何一档都没有存在意义，留着只会让「完整档没有、极简档有」这种不一致继续。

改法：

- `:1190-1195` 那根 `ProgressBar` **整块删除**（含 `IsIndeterminate="{Binding IsIndeterminate}"` 绑定）。
- `BoolInvertConverter` 不再需要用到这一处（它还有别的用处，不要顺手删）。
- 「任何一档都只有一根进度条，且都在卡片行底纹上」变成不变量，验收口径按这个写。

> 注意：`IsIndeterminate` 属性本身**保留** —— 它还要喂给底纹转换器的入参（§2.2：不确定态优先于 `StatusKind`）。删的是那根看得见的条，不是这个状态位。

### 2.6 百分比 / 时间：从底部行搬进卡片

> **2026-11-28 变更**：早先方案是「百分比 + 时间与段 2 合并成底部一行」。第四轮之后**轻量三档连底部这一行都不要了**。

- **完整 / 列表两档**：底部合并行保留（`31% · 已用 00:12 · 剩余 00:26` + 左侧元信息），因为这两档卡片已经占满一行、13 张卡塞不下时间。
- **轻量三档（极简 / 标准 / 详细）**：`PercentComplete` + 已用 + 剩余**各自成为一张卡片**（§2.11），底部合并行 `IsVisible=false` 整条隐藏。信息区只剩「底纹 + 一行卡片」，这是 `SizeToContent="Height"` 下最省高度的形态。

由此得到高度账：轻量档 = 视图行 + 卡片行 = **2 行**；完整 / 列表档 = 视图行 + 卡片行 + 底部行 = **3 行**（§2.8）。

**扫描态的特殊处理**：轻量档第一张卡（「进度」）在扫描期变身成「已发现 1,248」，卡标题写「已发现」、数值写 `1,248`、副行写 `12.4 GB`；同行的「已处理 / 总数量 / 速度 / 并行」四项一律写 `—`（扫描期这些数字没有意义，留着会被误读成「已完成」）。这条规则写进验收口径。

### 2.7 视图切换：两行合并成一行五档

现状是**两套互不相干的枚举各占一行**：

| 行 | 控件 | 绑定 | 取值 |
|---|---|---|---|
| 内容模式 | `RadioButton` × 3（`:296-320`） | `ProgressViewModel.ContentMode` | `ProgressContentMode { Simple, Detailed, List }` |
| 信息密度 | `RadioButton` × 3（`:645-651`） | `ProgressViewModel.InfoDensity` | `ProgressInfoDensity { Minimal, Medium, Full }` |

这是 issue #81 第 2 条的核心病灶 —— 「简约」（ContentMode）与「精简」（InfoDensity）两个近义词各表示一次"少"，用户无法区分；且 `IsMinimalDensity` 全 XAML 里只出现在它自己那个 `RadioButton.IsChecked`（`:655`），**没有任何内容绑定它**，所以「精简」档实质上不改变任何东西。

**改成一个 5 档控件**，内部映射两维度：

| 档位 | ContentMode | InfoDensity | 用户看到什么 |
|---|---|---|---|
| 极简 | `Simple` | `Minimal` | 只有压缩包名 + 总体进度 |
| 标准 | `Simple` | `Medium` | + 中等单行 + 批列表 8 行 |
| **详细**（新增，用户提议） | `Detailed` | `Medium` | 详细列表 + 批列表 8 行 |
| 完整 | `Detailed` | `Full` | + 13 张统计卡（底纹版，三行） + 批列表 11 行 |
| 列表 | `List` | `Full` | 纯列表视图 + 8 张卡（5 可点 + 3 只读，底纹版） |

**五档是单调递增的阶梯**，用户不必理解两个维度。

**迁移**：

- 新增 `AppSettings.ProgressDetailLevel`（枚举 `ProgressDetailLevel { Minimal, Standard, Detailed, Full, List }`）。
- 两个旧字段 `ProgressContentMode` / `ProgressInfoDensity` **保留不删**（老配置读得到；写完新字段后旧字段不再被读）。
- 读不到 `ProgressDetailLevel` 时按旧两字段反推：`Minimal→极简` / `(Simple,Medium)→标准` / `(Detailed,Full)→完整` / `(List,*)→列表`；被丢掉的 4 种组合（`Simple+Full` / `Detailed+Minimal` / `List+Minimal` / `List+Medium`）映射到相邻档。
- 存量测试里若有断言这两个字段的，需同步。

**宽度风险**：5 个单选 + 标签 + 「完整 \| 列表」之间的分隔线，再加右端的冲突下拉。**500 宽原型实测放得下**（视图段 ~195px + 间距 10 + 冲突 ~197px ≈ 402px，内容区约 468px，余 66px）⇒ 不需要折行兜底。若将来标签变长：优先缩标签（三档兜底：收紧间距 16 → 12 / 标签缩两字 / 改图标分段控件），**不要**把冲突下拉改成纯图标 —— 六档策略名靠文字承载，图标无法自解释。

| 10 | 720 + 36 = 756 | ✗ 溢 38px |
| **13（全量）** | 936 + 48 = 984 | ✗ 溢 **266px** |

⇒ **「完整档一行放下」只在「最多 9 张可见」时成立**。13 张全量必然折两行（原型实测 866px 高度已按折行算）。这是可接受的：卡片行折行时底纹仍只盖第一行高度，视觉上像「一根被卡片截断的进度条」，不算崩。真正要保证的只有一件事 —— **不同档位切换时卡片行高度不要乱跳**，这靠 `WrapPanel` 的自然高度 + `SizeToContent="Height"` 达成。

若将来要求 13 张卡必须一行：卡片压到 ~52px（13 × 52 + 12 × 4 = 724，刚好）—— 但 52px 下「41.76 MB」放不下，会截断。**结论：不追求 13 张一行，接受折行。**
